Face matching is two separate machine-learning problems wearing one name — finding a face, and telling faces apart. SnapFind tests them separately, then together, because a combined test can tell you which setup wins without ever telling you why. This is the full case: what each model does, why three different comparisons were needed instead of one, and what all three found.

THE PIPELINEThree steps, two different ML problems

"Face matching" sounds like one model. It's three steps, and the first two are built from completely different networks solving different problems — which is the reason this page has three sets of results instead of one.

Step 1 — Detect

Where is a face?

A detector takes a whole photo and returns bounding boxes — one per face, wherever they are. It has no idea whose face it is; it's a pure "find the object" problem, the same family as detecting cars or street signs. SCRFD, the model SnapFind uses, is a compact CNN trained specifically on faces.

→

Step 2 — Embed

Turn a face into numbers

An embedder takes one cropped, aligned face and outputs a 512-number vector — a point in space where faces of the same person land close together and different people land far apart. This is the actual "recognition" model; ArcFace and MobileFaceNet (below) are both embedders, trained differently, producing incompatible spaces.

→

Step 3 — Compare

Cosine distance

Two embeddings, one number: how far apart they point. Below a threshold counts as a match. This step has no model at all — it's arithmetic — so every result on this page ultimately comes down to how good steps 1 and 2 were.

Detector and embedder are orthogonal failures. A great embedder fed a bad crop (the wrong face, or a face cut off at the edge) produces a bad match — the embedder never gets a fair shot. A weak embedder fed a perfect crop still confuses people who look alike. Testing the whole pipeline at once can tell you the combination is wrong; it can't tell you which half is responsible.

METHODWhy three comparisons, not one sweep

The most trustworthy test is the last one on this page — real photos through the real API, real database, real worker. It's also the coarsest. It answers "which config wins" without decomposing why, and it never re-tests some choices at all.

None of the three is redundant. The sweep is staged in four steps specifically so it can approximate an answer to "why" — isolating the detector fix from the embedder swap by changing one at a time — but it still can't tell you SCRFD beats opencv, because it never runs opencv. That fact only exists in the detector comparison.

PART 1Choosing the detector

Three detectors, identical input, embedder held constant at ArcFace throughout — so any difference in results is purely about how well each one finds a face.

insightface / SCRFD-500MFLightweight ONNX30/30 · 100%283ms

opencv's Haar cascades are a pre-deep-learning technique — fast because they're doing almost no work, and it shows: they missed nearly half the faces in this sample, mostly at an angle or partially obscured. retinaface fixed that with a real CNN, but DeepFace's implementation is hardcoded to a ResNet50 backbone, and paying 14 seconds per photo does not scale to a 500-photo album. SCRFD is purpose-built to be small — 51× faster than retinaface, while finding more faces than either alternative. That's why it's the detector for both event photos and, per the sweep below, the selfie too.

Where it actually matters: real photos

The synthetic corpus is LFW faces composited onto generated backgrounds — controlled, but not what a phone camera produces. Eight real photos are the harder, honest test. Every one contains the target, so this measures recall only; with no negatives, precision would read 1.000 by construction and mean nothing. The real question: how far does each model's threshold have to move to recover every real photo, and what does that cost back on the labelled corpus, where false positives are measurable?

ModelThreshold for 8/8 realSynthetic precision thereSynthetic false positives there

w600k_mbf recovers every real photo while making zero mistakes on the labelled corpus. ArcFace can only get there by opening the threshold so wide it produces 43 false positives — it cannot find these photos and stay usable at the same time.

Port validated before any of this was trusted

Wrong preprocessing on an ONNX model still returns a confident, correctly-shaped, meaningless vector — it fails silently. w600k_mbf's output was checked against insightface's own reference implementation on identical input before any comparison ran: cosine distance 0.00000000.

PART 3Does it hold up end-to-end?

Not four independent runs — one change at a time, each measured before the next was made.

Does the bigger model actually win?

Stage 4 exists to answer one question: is mbf's size the whole story, or is it leaving real accuracy on the table? On the 163-photo synthetic corpus, it's an exact tie — identical precision, recall, F1, zero false positives for both. The only place they differ is real-job recall, 0.875 vs 0.750.

The honest limit of that number

That gap is one photo out of eight. Not enough evidence to call mbf more accurate than r50 on real photos — read it as a tie, decided by mbf also being 2× faster and 13× smaller. An easy call, just not an accuracy win.

Port validated inside the real pipeline this time

Both models checked against insightface's reference implementation from inside the actual worker container, against face_matcher.py's real code — not a separate copy. w600k_mbf: 0.0. w600k_r50: 2.22e-16 (floating-point noise). Both pass.

CAVEATSWhat these numbers are not

  • Small real-photo counts. 8 photos back the mbf-vs-r50 tie-break, 16 back the selfie-fix comparison. A difference of one photo moves these numbers a lot — read small gaps as noise, not signal.
  • The synthetic corpus is composited. LFW faces pasted onto generated backgrounds at controlled sizes — it isolates the face-size axis cleanly, but has none of the motion blur, mixed lighting, or odd angles of real event photography.
  • Ten identities, all public figures. No meaningful diversity in age or ethnicity, which is exactly where face models are known to degrade.
  • CPU, on a dev machine without AVX2/FMA. Absolute timings will differ elsewhere; the relative ordering should hold, since every config was measured identically.
  • Nothing here has run on a phone. This proves which model to use, not that an Android port of it detects and aligns faces identically — that's a separate port-validation question for whenever real on-device detection code exists.
