FINDING 01The pipeline is cautious, not careless

Precision 0.957 against recall 0.761 is a lopsided result, and the direction matters: only 3 false positives in 165 photos. It rarely shows you a stranger. What it does instead is miss people — 21 photos where the target was present and never surfaced.

For this product that's the better failure to have. A wrong face in someone's results is worse than a missing one they can find by loosening the threshold. But recall is where the remaining work is, and the cause is more specific than "the model is weak."

The largest single cause

25 of the 165 photos had no face detected at all. The embedder never saw them, so no threshold could have rescued them. That is the biggest bucket of failures by some distance — detection, not matching.

FINDING 02Face size decides almost everything

The synthetic corpus varies one thing deliberately: how many pixels wide the target's face is. Everything else — lighting, pose, background — is held constant. The result is a clean gradient.

Outlier worth investigating

job05 Gerhard Schroeder — F1 0.444. Only 2 of 7 found, and just 2 photos had no face detected. So three photos were detected and still scored too far away. That is a matching failure, not a detection one, and the only job in the corpus where that's true.

Honest caveat

real 6fe1d707's perfect 1.000 is inflated. Its selfie is byte-identical to one of its own four event photos, so one match is guaranteed at distance 0.0195 — the pipeline is scoring an image against itself.

The most actionable defect on this page

real 24c8ea7c fails by a hair — 0.691 and 0.705 against a 0.68 cutoff. That is not a model that can't recognise the person; it's a model being handed a poor crop of them.

The selfie path still downscales to 1024 px, detects with mtcnn, and takes whichever face the library returns first. Event photos were fixed to detect small and crop from the original; the selfie never was. Swapping the selfie to the same detector and largest-face selection takes this job from 0/4 to 2/4, measured.

Why this sweep was worth re-running

Against the broken pipeline, the same sweep put the optimum at 0.85. Calibrating then would have baked the downscale bug into the threshold and hidden it permanently. Fix the pipeline, then tune the number — not the other way round.

On the real photos, it is decisive

The synthetic corpus is LFW faces composited onto phone-sized canvases. The eight real photos are the actual product input, and they are the harder case. Every one contains the target, so this measures recall only — with no negatives, precision there would read 1.000 by construction and mean nothing. The honest question is how far each model's threshold has to move to recover all eight, and what that costs back on the labelled corpus where false positives are measurable.

ModelReal photos at its own thresholdThreshold for 8/8Synthetic precision thereSynthetic FP there
DeepFace ArcFace current6/8 at 0.650.900.60643

w600k_mbf recovers every real photo at 0.70 while still making zero mistakes on the labelled corpus. ArcFace can only reach all eight by opening up to 0.90, and at that point it produces 43 false positives and precision collapses to 0.606 — it cannot find these photos and stay usable at the same time. That is a different claim from the synthetic table above, and a much stronger one.

Status

Measured, not adopted. Production still runs DeepFace ArcFace. Switching invalidates every cached embedding and needs the threshold re-derived, so it is migration work rather than a config change.

The ONNX port was validated against insightface's own reference implementation on identical input — cosine distance 0.00000000 — before any of these numbers were trusted. Wrong preprocessing returns a confident, correctly-shaped, meaningless vector, so this check comes first or the comparison is worthless.

Caching helps less than advertised

Re-running a job with its embeddings already cached is only 1.4× faster, not the "nearly instant" the docs claim. Part of that is the selfie embedding, which is recomputed on every run at roughly 3.3 s — event photos are cached, the selfie is not. The remaining gap has not been isolated.

It matters less than it looks: caching only pays off when the same job is processed twice, which in practice means a threshold change, not a re-upload.

METHODHow these numbers were produced

Through the real API, not around it

Every job was uploaded exactly as a phone would: upload/init, presigned PUTs straight to object storage, a multipart zip, then complete. The worker extracted each archive and ran the production matcher. Nothing read photos off disk behind the API's back, so these numbers describe the shipped pipeline.

Labels live in the filenames

p03_pos_240px.jpg already states the answer and the face size, and the pipeline preserves it as original_filename. There is no ground-truth file to drift out of sync with the photos. The three real jobs carry no marker, so their labels are the one thing recorded by hand.

What these numbers are not

  • The synthetic corpus is composited. LFW faces pasted onto generated backgrounds at controlled sizes. It isolates the face-size axis cleanly, but it has none of the motion blur, mixed lighting or odd angles of real event photography.
  • Twelve real photos is not a sample. One person, one trip, one outfit. They can show a failure exists; they cannot measure how often it happens.
  • Ten identities, all public figures. No meaningful diversity in age or ethnicity, which is exactly where face models are known to degrade.
  • CPU on a dev machine without AVX2/FMA. Absolute timings will differ elsewhere; the relative ordering should hold, since all variants were measured identically.
